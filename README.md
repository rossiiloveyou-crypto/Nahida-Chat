# Nahida Chat 功能与使用手册

> 适用版本：**`1.0.0`**（首个正式发布版）
> 文档基线：**2026-11-15**（本文件只描述已落地的行为）
> 覆盖范围：P0–P8 全部落地内容 —— 记忆按「用户 × 人设」分库、长期记忆面板、**区块（Zone）已移除**、
> **清空全部数据**、**SillyTavern（ST）桥接**、**ST 正则显示层（标签卡片 + 对白高亮）**、
> **消息编辑 / 重发 / 删除**、**RAG 模型一键下载**、**Windows 安装包（NSIS）**。
> 本文描述**已落地行为**；未实现的密钥加密等能力单独标注，不作为现成功能。

## 1. 项目定位

Nahida Chat 是一个**本地优先的桌面 AI 对话客户端**，基于 Electron + Vite + React + TypeScript。

它适合这些使用场景：

- 在桌面上与可配置的模型服务对话，按角色文件夹切换人格与说话风格；
- 让模型在指定的本地工作区里列出目录、读取文件、查看时间；
- 建立一个独立的“故事区”，在角色设定之上继续写剧情，并保留分支、画像与世界书；
- 把 QQ 私聊/群聊作为外部渠道接入，由白名单控制谁能触发、谁能用工具；
- 在本地保存对话、配置与长期记忆，并让记忆以可审计的方式参与下一轮对话；
- 需要彻底重来时，可以把**所有人**的会话、记忆、人设历史、摘要与故事区一键清空
  （设置与授权保留，清完应用自动重启，见 8.7）。

它**不**是一个会自动上传数据的云端服务：桌面会话、故事、记忆、提示词与密钥都以本机文件为真源。启用远程模型或 QQ 时，相关请求自然会发往对应服务商或 QQ 客户端；这一点在“数据与隐私”一节会逐项说明。

## 2. 快速开始

### 2.1 环境要求

- Node.js `^24.22.1 || >=26.12.1`（`package.json` 的 `engines`）；
- pnpm **`11.25.0`**（`package.json` 的 `packageManager`，用 corepack 自动切）；
- 打包安装包需要 pnpm `11.25.0`（`electron-builder` 与 Snowluma 宿主构建都要它）；
- Windows 桌面环境（当前主要开发/验证平台；Electron 本身跨平台，但 QQ 注入属于 Windows 场景）。

### 2.2 安装与启动

```bash
corepack enable
pnpm install
node .\node_modules\electron\install.js
pnpm dev
```

首次启动默认使用**演示模式**：回复由本地 mock 生成，不调用远程模型。可以先用它验证“输入 → 流式显示 → 会话落盘”的完整链路。

### 2.3 接入真实模型（最短路径）

1. 打开左下角 **设置 → 模型配置**。
2. 点 **新建档案**，选择一个预设（OpenAI、DeepSeek、Kimi、通义千问、智谱、火山方舟、MiniMax、OpenRouter、Anthropic、Gemini、Ollama 或自定义 OpenAI 兼容服务）。
3. 按预设填写或确认 `baseUrl`、`apiKey`，在模型清单里添加模型 ID。
4. 点 **测试连接**；通过后点 **保存档案**。
5. 将这套档案 **设为默认**。不手动切换模型的对话和 QQ 渠道都会跟随默认档案的默认模型。

> `apiKey` 当前以明文写入 `userData/settings.json`。请不要把该文件提交到 Git、上传到工单或共享给他人。项目尚未实现 safeStorage 加密。

### 2.4 日常使用入口

左侧栏从上到下是：

- **新建对话**：创建一条普通 Chat 会话；
- **最近**：当前活动工作区下的普通会话（故事与 QQ 会话不会混入这里）；
- **故事**：故事卡片与 **+ 新建故事**；
- **设置**：模型配置、系统提示词、故事区、长期记忆、渠道控制台、QQ 接入、工具权限、外观、关于。

主对话区底部有四个选择器（从左到右）：

- **角色**：这个对话由谁扮演，切完下一轮就换人格（见 5.4）；
- **模型**：只影响当前会话，切到其他模型不会改默认档案；
- **工作区**：Agent 工具可访问的目录边界；
- **权限**：只读 / 审批 / 完全访问。

输入 `Enter` 发送，`Shift + Enter` 换行；中文输入法组词期间按 `Enter` 不会被误发送。输入超过 100,000 字只标红提醒，不硬截断。

## 3. 对话模式

### 3.1 Chat

新建对话首页的 Chat 滑块对应纯对话模式：

- 默认不会向模型提供工具；
- 仍会注入系统提示词、当前时间与已启用的长期记忆；
- 如果需要在 Chat 里使用工具，必须额外开启下文“Chat 工具增强”，并逐个勾选允许的工具。

Chat 适合日常问答、写作、角色聊天，以及不希望模型改动本地文件的场景。

### 3.2 Agent

Agent 模式面向“让模型读工作区、执行工具”的任务：

- 会向模型提供当前可用的工具定义；
- 工具是否执行由 **工作区 + 权限模式 + 渠道授权**共同决定；
- 没有任何工作区时，输入区会进入门禁态并提示先创建工作区；
- 一个会话开始有消息后不能直接切模式；要换模式请新建对话。

### 3.3 Story（故事区）

故事模式不是首页第三个滑块，而是从侧栏 **故事 → + 新建故事** 进入。每条故事区拥有：

- 自己的角色、标题、概要、背景设定；
- 自己的分支与分支消息（每条分支就是一条会话，分支之间**互相独立**）；
- 自己的长期记忆库；
- 可选的剧本世界书与故事画像。

故事会话不会出现在“最近”列表里，避免与普通对话混杂。

### 3.4 模式切换规则

- 空会话可以在 Chat / Agent 之间切换；
- 已有消息的会话锁定模式，新建对话才能切换；
- **角色不受这条限制**：随时可在对话页切换，历史消息不动，下一轮就换人格（见 5.4）；
- 故事区保持 `story` 模式，不会被塞回 Chat 滑块；
- 故事会话不向模型提供工具，工具只属于 Chat/Agent 的可配置能力。

### 3.5 思考过程（支持推理的模型）

接了会「先想再答」的模型时，回答上方会出现一个折叠块，显示模型的思考过程——
和 DeepSeek 网页里的观感一致。

- **思考中**：块自动展开，正文逐字追加，末尾带闪烁光标；这期间输入框显示「停止生成」，
  随时可以中断；
- **开始回答**：块**自动收起**，只留一行「已思考 · N 字」，点击可再展开回看；
- **手动展开/收起过之后**，就不再自动收了（否则读到一半被收走很恼人）。

支持的服务商与字段：

| 服务商 | 协议字段 | 说明 |
| --- | --- | --- |
| DeepSeek / 通义千问 / 智谱 GLM / Kimi（OpenAI 兼容） | `delta.reasoning_content` | 最常见的一种 |
| OpenRouter 及部分中转 | `delta.reasoning` | 字段名不同，已一并识别 |
| 少数自建网关 | `delta.thinking` | 兜底 |
| Anthropic | `thinking_delta` | 需在服务端开启 extended thinking |
| Gemini | `parts[].thought === true` | 思考与正文共用 text 字段，靠 thought 位区分 |
| Ollama | `message.thinking` | 0.6+ 的 thinking 模型 |

**三条边界，都是刻意的**：

1. 思考**只做展示，绝不回灌**下一轮。DeepSeek 官方明确要求不要把 `reasoning_content` 传回去（会 400），
   而且思考常常几万字，回灌等于每轮 token 翻倍。实现上 `sessionHistoryToLlm` 只取 role/content，天然不带它。
2. 思考**不进正文**：不会被当成回答内容落库到 `content`，也不会被 QQ 发到群里。
3. 演示模式（离线 mock）**也会**产生一段思考文本，开头明写「这是演示模式的思考过程」，
   首装就能看到这个块的完整形为，不冒充真实推理。

> 模型没返回思考时（绝大多数普通对话），这个块完全不出现，界面与改动前一致。

### 3.6 出错、中断与重试

一次请求失败（Key 过期、连不上、服务端 5xx、模型中途断流）时，**那一条回复**会变成失败态：

- 气泡里写明原因（例如 `fetch failed`、`401 Unauthorized`），不再是三个点的转圈动画；
- 气泡下面给两个键：**重试这一轮** / **删除这条**；
- 原因会跟着消息一起落盘，重开应用后仍然看得到（关掉顶部红条也不会丢）。

**重试**的语义是「重跑这一轮」，不是「再发一次话」：

| 行为 | 说明 |
| --- | --- |
| 复用那条回复 | 同一个 message id，正文/思考/工具记录清空后重跑 |
| 不新增用户消息 | 历史里不会出现两句一样的原话，侧栏条数也不虚增 |
| 只对最后一条生效 | 中间那条重跑会把后面的上下文截断，所以键只出现在最后一条；<br>已翻篇的那些只保留「删除」 |

另外两种情况也归到同一个失败态，因为它们看起来一模一样、用户分不出来：

- **点了停止**：正文是空的 → 气泡写「这一轮没有内容（可能被停止……）」，可以重试；
- **应用被关掉/崩溃**：盘里留下 `streaming` 的半截回复 → 下次启动读盘时自动改成失败态，
  并注明「上次生成没有跑完」，同样可以重试（半截正文保留，看得见它断在哪）。

删除只删**那一条**（用户那句原话保留），所以「问话还在、回答重来」是常态。

### 3.7 消息编辑、重发与删除

每条消息下面是一排图标按钮（悬停显示文字提示），从左到右按可用性出现：

| 动作 | 作用范围 | 说明 |
| --- | --- | --- |
| **编辑** | 你的消息与旁白 | 原地改正文，两个出口：**保存不发送**（只改字）／**保存并重新提问**（改完丢弃其后的全部消息并重跑一轮，有二次确认） |
| **重试** | 最后一条助手回复 | 重跑这一轮，不新增用户消息（见 3.6） |
| **删除** | 所有消息 | 删掉**这一条**，后面的对话保留；删除后它不再出现在上下文里 |
| **复制** | 有正文的消息 | 复制落库原稿（不是渲染后的显示文本），复制成功图标短暂变成勾 |

三条边界：

- **渠道会话（QQ）只读**：消息来自外部真源，桌面改一条会让两边不一致，所以那里**不渲染**这些按钮；
- **生成中禁用**：有生成在跑时编辑/删除按钮置灰，提示「先停止」；
- **编辑态锁发送**：编辑框打开时输入区的发送键禁用，避免「保存」与「发送新消息」抢同一个落点。

> 空内容不当作编辑：想让一条消息消失，唯一入口是**删除**（落盘、有确认、留痕），
> 不是把它改成空串。

### 3.8 显示效果：markdown、标签卡片与对白高亮

气泡正文不是纯文本插值，而是一条**显示管线**（只影响显示，落库永远是原稿）：

1. **ST 正则（markdown 通道）**——读 `settings.json` 里的 `regex_scripts`，只跑 `markdownOnly` 且命中 `AI_OUTPUT` 的脚本。
   `promptOnly` 脚本由 SillyTavern 自己在组装请求时执行，这里**不重复跑**（否则同一句改写会生效两次）。
2. **标签卡片**——预设（如「浪潮」）常把 `<wave_plan>`、`<wave_summary>` 这类标签替换成一整段 HTML 面板。
   NC **不托管那段 HTML**（那是 iframe 宿主，永久不做），而是识别出「这条脚本被 M9 拦下」后，
   用**自己的折叠卡**显示标签内的纯文本：八种标签映射成六类中文标题，默认收起，展开是纯文本。
3. **markdown 渲染**——粗体、标题、代码围栏、列表等正常呈现；产物过 DOMPurify 白名单。

**对白高亮**：六种引号（`"…"`、`“…”`、`«…»`、`「…」`、`『…』`、`＂…＂`）按 ST 同款规则包成 `<q>` 并上橙色。
包裹只作用在文本节点，代码块、行内码、HTML 属性与链接标题**不受影响**。

## 4. 模型配置

### 4.1 模型档案（ModelProfile）

“模型档案”是模型配置的唯一真源，包含：

- 档案名；
- 传输适配器（演示、OpenAI 兼容、Anthropic、Gemini、Ollama）；
- 服务地址与 API Key；
- 模型清单、默认模型；
- 温度（0–2）；
- 每个模型的上下文窗口与是否多模态（用于界面提示与后续裁剪判断）。

设置页里的扁平字段（provider/baseUrl/apiKey/model）只是镜像；聊天时会重新解析档案，避免使用过期镜像。

### 4.2 可用预设

| 预设 | 传输适配器 | 说明 |
| --- | --- | --- |
| 演示模式 | mock | 完全离线，本地回显 |
| OpenAI | OpenAI 兼容 | OpenAI Chat Completions |
| DeepSeek | OpenAI 兼容 | DeepSeek API |
| 月之暗面 Kimi | OpenAI 兼容 | Moonshot API |
| 通义千问 | OpenAI 兼容 | DashScope 兼容模式 |
| 智谱 GLM | OpenAI 兼容 | 智谱开放平台 |
| 火山方舟 | OpenAI 兼容 | 火山方舟 |
| MiniMax | OpenAI 兼容 | MiniMax API |
| OpenRouter | OpenAI 兼容 | 聚合模型服务 |
| Anthropic Claude | Anthropic | Messages API |
| Google Gemini | Gemini | streamGenerateContent |
| Ollama（本地） | Ollama | 本机 11434 端口 |
| 自定义（OpenAI 兼容） | OpenAI 兼容 | 任意兼容接口 |

预设只负责预填，不锁定；地址和模型都可以改。

### 4.3 添加模型与获取清单

- 服务商实现模型清单接口时，点 **获取可用模型**，勾选后一次性加入；
- 服务商不实现或请求失败时，直接在输入框填模型 ID 后回车/点“添加”；
- 模型清单至少保留一个模型；移除当前默认模型前，请先选新的默认模型；
- “测试连接”使用当前草稿，不要求先保存档案。

### 4.4 单会话模型切换

输入框下方的模型选择器写入当前会话：

- 不会修改默认档案；
- 正在生成的那一步不受切换影响，下一次请求才使用新模型；
- 没有会话时选择会暂存为“下一句话”的模型，建立会话后带入。

### 4.5 渠道模型

QQ 私聊/群聊没有独立模型选择器，固定使用**默认档案的默认模型**。想换渠道模型，请改默认档案或其默认模型；这会同时影响没有手动切换模型的桌面对话。

### 4.6 ST 桥接（故事模式由 SillyTavern 生成）

故事区可以把**生成这一环**交给本机的 SillyTavern（下称 ST）跑：人格、世界书、历史仍由 NC 拼好送进去，
**ST 只负责请求与它自己的预设注入**（典型用途是借 ST 的破甲预设）。

**开关**：设置 → ST 桥接。开之前请先在后台启动 ST（`node D:/ST/SillyTavern/server.js`），
并保持运行；NC 不会替你启动 ST，关掉浏览器页面不影响已启动的服务。

**生效条件（三者同时满足）**，写在一个纯函数 `bridgeEligible` 里，全仓唯一判定点：

```text
会话是 story 模式  ∧  不是渠道会话  ∧  settings.bridge.enabled === true
```

任一不满足就走原来的 provider 路径，**逐字回到旧行为**。

**桥接生效时模型选择置灰**：这一轮由 ST 生成，模型在 ST 里设；置灰不只是样式，回调也被拦住。

**NC 做这三件事**：

| 环节 | 做法 |
| --- | --- |
| 历史 | 只搬 user / assistant，逐字；system 段**不进 chat**，改灌 ST 的 `extensionPrompt` |
| 清场 | 每轮进出各清一次 `chat` / `chatMetadata` / `extensionPrompts`；**不用** `resetChatState`（它会清空角色并塞 SAFETY_CHAT） |
| 成败 | 只认 `await ctx.generate('normal')` 的 resolve / reject；空串按失败处理（不可靠的「生成结束」事件不算判据） |

**开关锁**：ST 的 `auto_continue` / `auto_swipe` 会在轮内被临时置 false 并**必定还原**（失败也还原），
只改页面内存、不写 ST 的 `settings.json`。

**零持久化**：桥接拦截对 ST 的写盘请求（`/api/chats/*`、`/api/backups/*`、`/api/settings/save`、
`/api/quick-replies/save`）与非 127.0.0.1 的外网请求。切分支、跑多少轮，ST 侧磁盘都不变。

**失败怎么显示**：ST 超时会调 `stopGeneration`；reject / 空回复 / 超时三类都会带上 ST 给出的原因
（含页面 toast 文案），气泡按 3.6 的失败态展示，可直接重试。

## 5. 提示词与角色

### 5.1 提示词目录

提示词是用户资产，程序不写死任何角色人格。目录结构如下：

```text
Prompt/
├─ shared/
│  ├─ base.md                 全局底线规则（所有角色、所有模式）
│  ├─ tone.md                 语气与句式（所有角色、所有模式）
│  └─ tool_usage.md           工具规范（仅 Agent）
└─ characters/
   └─ <角色 id>/
      ├─ soul.md              人格核心
      ├─ canon/*.md           原作台词样本（可选）
      ├─ worldbook/*.md       背景设定
      ├─ modes/{chat,agent,story}.md   各模式规则
      └─ styles/{chat,agent,story}.md  各模式表达风格
```

实际拼装顺序是：

1. `shared/base.md`
2. `shared/tone.md`
3. `characters/<id>/soul.md`
4. `characters/<id>/canon/*.md`
5. `characters/<id>/worldbook/*.md`（故事“完全覆盖”档位时跳过）
6. 剧本世界书 `worldbookDir/*.md`（故事区可选）
7. 故事背景与剧本设定（故事区可选）
8. `characters/<id>/modes/<mode>.md`
9. `characters/<id>/styles/<mode>.md`
10. 故事用户画像 `profile.md`（故事区可选）
11. `shared/tool_usage.md`（仅当本轮真有工具）

缺哪个文件就跳过哪个，不报错。

### 5.2 在设置页做什么

**设置 → 系统提示词**只做三件事：

- 展示注入顺序与“改哪个文件”；
- 打开整个提示词目录或某个角色目录；
- 将某个角色设为「新对话默认」。

> 日常换角色**不用**来这一页：对话页输入区最左的选择器就能切（见 5.4）。这一页管的是「改哪个文件」。

设置页**不显示也不编辑提示词正文**，正文请用外部编辑器直接改 `Prompt/` 下的文件。这样只有一份真源。

### 5.3 新增角色

1. 在 `Prompt/characters/` 下新建一个文件夹，文件夹名就是角色 id；
2. 至少写 `soul.md`，否则设置页会标为缺少人格核心；
3. 按需添加 `worldbook/`、`canon/`、`modes/`、`styles/`；
4. 回到 **设置 → 系统提示词**，刷新或重新进入页面即可看到新角色；
5. 对话页输入区最左的「角色选择」里会直接出现它，点一下就能切过去（见 5.4）；
6. 也可以在设置页把它设为「新对话默认」，或新建故事时选择该角色。

不需要改代码。

### 5.4 切换角色（对话页）

对话页输入区最左的那个选择器就是角色入口（名字首字 + 角色名 + 箭头）：

![角色选择](docs/ui/ui-map-v0-chat-conversation.png)

点开是**提示词库里的全部角色**，每一条带角色 id；缺 `soul.md` 的角色也在列，但是灰的、点不动
（列出来才好解释「为什么清单里少了一个」）。

| 操作 | 结果 |
| --- | --- |
| 在对话中切换 | 当前会话的 `characterId` 改掉，历史消息一个字不动，**下一轮**就换成新的人格与说话风格 |
| 新建对话 | 跟随最后一次选择 —— 切换器同时写了「新对话默认角色」 |
| 故事会话 | 选择器是灰的：故事的角色属于故事区本身，去 **设置 → 故事区** 改 |
| 缺 `soul.md` 的角色 | 列在菜单里但置灰，选中它等于「谁都不扮演」 |

三条设计决定：

1. **切换写两处**（会话 + 新对话默认）。只写会话的话，切换完一新建对话又回到默认角色，
   等于把「靠新建对话换角色」换个方式留着 —— 而这次要改掉的正是它。
2. **主进程会校验目录真实性**。拼错或角色目录被删时报错，而不是让提示词拼装悄悄跳过人格那几段 ——
   后者在界面上表现为「她忽然没了人格」，比报错难查得多。
3. **切角色不换记忆库**。长期记忆（8.1）按「用户人设」分域，不按 AI 角色分域，
   所以切换到另一个角色后仍会召回同一批事实记忆。要隔离记忆，请用故事区（8.4）。

### 5.5 世界书（Worldbook）

世界书是背景设定条目库。一个世界书是一个目录，目录里每个 `.md` 文件可包含多个条目；`README.md` 是索引，不会被当成条目文件。

每个条目的格式：

```markdown
## 条目名
- id: <32 位十六进制>
- 触发词: 钟楼, 报时, 停摆
- 常驻: 否
- 优先级: 5
- 内在价值: 50
- 连带触发词: 无

正文……
---
```

字段含义：

- **触发词**：命中后激活该条目；逗号、顿号都可分隔；
- **常驻**：为“是”时始终注入，不参与普通触发；
- **优先级**：1–10，激活后的排序 tiebreak；
- **内在价值**：0–100，抗遗忘基准；
- **连带触发词**：本条命中时顺带激活其它条目，一层封顶。

**设置 → 系统提示词 → 打开世界书编辑器**支持：

- 选择已知角色世界书或故事剧本世界书；
- 选择任意目录/任意 `.md` 文件；
- 新建世界书；
- 按标题或触发词搜索条目（大小写无关）；
- 新增、编辑、删除条目；
- 缺 `id` 的合规条目会保留并标记，保存时自动补 id；
- 同文件内触发词重复只提醒，不阻止保存；
- 写入目录有路径守卫，写入前保留 `.bak` 并原子替换。

编辑器默认先显示 8 条，其余通过“展开”查看；搜索会过滤当前列表，但不会修改磁盘上的条目顺序。

### 5.6 故事区专用设定

- **背景与剧本设定**：描述环境与场景，属于设定层，不是第一条消息；
- **用户画像 `profile.md`**：描述“你”在这个故事里是谁，只对本故事生效；
- **剧本世界书目录**：可指定一个独立目录；
- **世界书档位**：
  - **两段都注入**：角色 worldbook + 剧本世界书；
  - **完全覆盖**：只注入剧本世界书，跳过角色 worldbook。

“完全覆盖”必须提供剧本世界书目录，否则该故事的世界书会整段消失。

## 6. 故事区

### 6.1 新建故事

从侧栏 **故事 → + 新建故事** 打开表单，填写：

- 标题（必填）；
- 角色；
- 剧本世界书目录（可空）；
- 世界书档位；
- 背景与剧本设定（可空）；
- 开场消息（可空，非空时会写成该故事根分支的首条 assistant 消息）。

创建后会进入该故事的当前活跃分支。

### 6.2 分支

右侧 **分支** 抽屉是故事区的工作台：

- **检索**：在当前故事的全部分支里检索，点击命中可跳到对应分支和消息；
- **分支列表**：一条分支一行，显示消息数、最近活动时间，以及它是从哪条分支的第几条分出来的；点击可切换；
- **消息时间轴**：一个**定高窗口**，默认停在**最新一条**，向上滚看历史；每条消息后面都有「由此分支」，所以想从刚发生的这句分出去只需一次点击；
- 派生新分支会激活新分支；原分支不受影响；
- **分支之间互相独立**：派生完它就是一条自己的会话。之后删掉任何别的分支（包括它是从哪条分出来的），或者那条分支继续往下写，都不影响它的消息、检索和记忆召回；
- 可以删任何一条分支，**包括当前正在看的那条**——删完会自动切到最近活动的那一条；
- 唯一删不掉的是**最后一条**：删完这个故事就没有会话可进了；
- 删除分支不可恢复，确认框会提示消息数量。

分支复制的是分叉点之前的消息前缀；旁白也会作为消息一起复制。
列表里那句「从《某分支》第 N 条分出」只是**派生那一刻记下的快照**：源分支后来改名、继续写、甚至被删掉，这行字都不会变，也不参与任何计算。

### 6.3 检索

抽屉检索范围是**整条故事的所有分支**，不是只看当前分支。结果会显示：

- 所属分支；
- 消息序号；
- 角色（我 / 她 / 旁白）；
- 截断后的命中片段。

点击结果会自动切换到对应分支，并滚动、短暂高亮该消息。

### 6.4 旁白

故事输入框左侧有 **对话 / 旁白** 徽章。

使用“旁白”时：

- 输入内容**不调用 LLM**；
- 不创建用户消息，也不显示用户头像气泡；
- 消息区以居中文字显示“旁白：xxxxx”；
- 旁白会立即写入会话并持久化；
- 下一次发送普通“对话”时，旁白会作为独立的 **system** 消息、带“系统旁白：”前缀进入模型上下文；
- 正在生成时不能插入旁白，避免打乱本轮顺序。

普通 Chat/Agent 会话不显示这个徽章。

### 6.5 故事设置与删除

**设置 → 故事区**可以：

- 查看全部故事区；
- 修改标题、概要、角色、背景与世界书档位；
- 编辑用户画像；
- 查看/删除/清空该故事自己的长期记忆；
- 删除整个故事区。

删除故事区会连同该区记忆库与所有分支一起删除，**不可恢复**。程序会在删除前自动备份到 `stories/.trash/`，但不要把备份当成常规版本管理。

### 6.6 故事数据路径

每个故事区是自包含目录：

```text
userData/stories/<storyId>/
├─ story.json        元信息
├─ branches.json     分支列表（首次读取时可能懒迁移生成；老版本文件读到时自动升级）
├─ profile.md        用户画像（可不存在）
└─ memory.db         该故事自己的长期记忆库
```

删除前的备份位于 `userData/stories/.trash/`，不在被删目录内部。

## 7. 工作区与工具权限

### 7.1 工作区

工作区是一个本地目录，决定 Agent（以及开启工具增强的 Chat）能读写的根。支持多个工作区：

- 侧栏在 Agent 模式下显示工作区列表；
- 输入框下方也能切换当前会话工作区；
- 新建对话、设置当前活动工作区、删除工作区都会影响后续会话的默认落点；
- 删除工作区前请确认没有会话依赖它；删除后会话会被重新指派到其他活动工作区。

零工作区时，Agent 输入区会门禁，点击输入区可按引导创建目录。

### 7.2 三种权限模式

| 模式 | 只读工具 | 有副作用工具 | 路径 |
| --- | --- | --- | --- |
| 只读 | 直接执行 | 一律拒绝 | 限工作区内 |
| 审批（默认） | 直接执行 | 弹确认卡，超时按拒绝 | 限工作区内 |
| 完全访问 | 直接执行 | 直接执行 | 不受工作区限制 |

“只读/有副作用”由工具定义里的 `readOnly` 字段决定。切换权限后，下一轮工具调用立即按新配置执行。

### 7.3 当前内置工具

- `fs.list_dir`：列出工作区目录，最多显示 200 项；
- `fs.read_file`：读取文本文件，最多 64 KB，遇到二进制内容拒绝；
- `clock.now`：获取本机或指定 IANA 时区的当前时间。

工具错误不会炸掉整轮对话，而会作为工具结果回喂模型。

### 7.4 Chat 工具增强

Chat 默认拿不到任何工具。若需要：

1. **设置 → 工具权限 → Chat 工具增强**，打开总开关；
2. 在逐工具列表中勾选允许的工具；
3. 保留/调整全局权限模式；
4. 回到 Chat 会话发送消息。

总开关关闭时，Chat 拿不到工具；已勾选条目会保留。这里控制的是“是否供给”，最终执行还受权限模式与渠道授权约束。

## 8. 长期记忆（RAG）

### 8.1 能力概述

长期记忆是跨会话的事实库，不是把整段聊天全文入库。它主要记录用户说过的稳定事实，并通过检索在下一轮作为独立 system 段注入。

- 混合检索：向量相似度 + SQLite FTS5 关键词；
- 全链路本地 embedding，不把对话内容发去外部做 embedding；
- 模型缺失时降级为关键词检索，其余对话照常；
- 每轮开始时只检索一次，控制开销；
- 超预算整条丢弃，不切半句。

### 8.2 使用方式

**设置 → 长期记忆**从上到下是：对话摘要参数 → 运行状态 → 检索参数 → 检索调试 → **按人查看与清理** → **危险区**。

- 开关总开关、开关自动提炼；
- 调整召回条数 `topK`、token 预算、分数下限；
- 用一段话“试召回”，查看综合分/向量分/关键词分；
- **按人查看**：列表里每位用户一行（记忆条数 / 人设数 / 最近活动），点「查看」进详情 ——
  人设表、该人的记忆条目、近期聊天、**存储位置**（主库路径 + 租户 `(user_id, persona_id)`）与「打开目录」；
- **按人删除**：只删**那一个人**“记得的东西”，不动授权，他仍然能说话；
- **清空全部数据**：清所有人，见 8.7；
- 打开模型目录，按路径放置 embedding 模型。

### 8.3 一键下载 embedding 模型

模型体积较大（约 **587 MB**），不随仓库分发。**设置 → 长期记忆 → 运行状态**里点
**「一键下载并配置模型」**即可，不用手动放文件：

| 项 | 说明 |
| --- | --- |
| 落盘位置 | `%APPDATA%\Nahida Chat\models\Xenova\bge-m3\`（在 userData 下，升级/重装程序都不会丢） |
| 下载内容 | `config.json`、`tokenizer.json`、`tokenizer_config.json`、`onnx/model_quantized.onnx`（q8） |
| 镜像 | 先 `hf-mirror.com`，失败自动回退 `huggingface.co` |
| 进度 | 按钮下方显示当前文件、百分比与已下载/总量；分母是 HEAD 探测到的**真实体积** |
| 原子性 | 先写 `.part` 再改名，且逐个文件做体积校验；断网中断不会留下"看起来装好了"的半截文件 |
| 生效 | 装完清掉加载失败缓存，**下一次检索自动加载**，不用重启 |

模型目录也可以手动放（老做法仍有效）。缺少模型时不会报错阻断对话，只会降级为纯关键词检索。
具体下载来源、实测数据与设计细节见 [docs/04-RAG记忆检索设计.md](docs/04-RAG记忆检索设计.md)。

### 8.4 记忆域与故事记忆

- 记忆的真实分区键是 **`(user_id, persona_id)`**：同一个人在不同人设下是两套记忆，
  不同人的记忆互相不可见；桌面、私聊、群聊**不**按场景再切一层（「换场景不换人设」）；
- 桌面对话写入主记忆域；
- 故事区使用自己目录里的 `memory.db`，物理隔离；
- 故事分支记忆记录来源消息下标；派生分支时把「哪些分支的哪些记忆可见」固化进 `branches.json`（快照），之后召回只读这份快照：分叉点之后别处才产生的事实不会串进来，而删掉源分支也不会让子分支的记忆跟着消失；
- 某个故事区的记忆可在 **设置 → 故事区** 单独查看与清理；
- 早期“区块（Zone）”曾用来划分共享记忆域，**P6 已整体移除**（见 9.1）；

### 8.5 隐私边界

记忆检索与 embedding 在本机执行，但“记忆注入”会把命中事实交给当前模型。若使用远程模型，这部分内容会随请求发给服务商。不要把不愿发送的敏感事实放进记忆，或使用本地 Ollama。

### 8.6 对话摘要（与上面的 RAG 是两层）

上面 8.1–8.5 讲的是**事实记忆**：从你的发言里抽事实、按问题检索、命中才注入。
还有一层**对话摘要**，解决的是另一个问题——对话变长后，早期内容会掉出上下文窗口，
模型就此“失忆”，而这件事 RAG 管不了（它只存事实，不存对话）。

做法是滚动压缩：

- 每攒够 **触发条数**（默认 40 条可读消息），后台把这段对话压成四段：
  **近期话题 / 你的信息 / 重要约定 / 长期经历**，并记下“已经压到第几条”；
- 每轮请求注入这四段摘要，**历史只下发最近「保留窗口」条（默认 12）**；
- 于是上下文长度是**常数**，长对话不会因为超出窗口而丢前文。

四段是一次压缩的 4 个并发请求；压缩在后台跑，**不阻塞当前回复**，那一轮仍用旧摘要。
任一段失败就不推进边界（下一轮重试同一批），失败后 60 秒内不再重试。
撤回消息、重新生成、切换故事分支会让“边界锚点”失效，此时**整份摘要作废、自动回落全量历史**，
不会用过期下标切出一段错位的历史。

在 **设置 → 长期记忆** 顶部可以调：总开关、触发条数、保留窗口、四段各自字符上限，
并看到「已摘要会话 / 已压缩消息 / 上次更新时间 / 数据文件」。
两个按钮：「忘掉当前会话的摘要」（只删摘要，不动聊天记录）与「清空全部摘要」。
**改完立即生效，不需要重启**（数字框在失焦或回车时才落地，打字过程中不会被打断）。

边界（刻意的）：

- 演示模式（离线 mock）下不压缩——假模型压出来的四段是假文本，写进库比不写更糟；
- 工具结果**不进摘要**。工具输出是不可信外部内容，进摘要等于把它永久固化进每一轮 system 提示词；
- 摘要里被压缩掉的细节不可恢复。需要原文就去聊天记录里翻——摘要只保证“接得上”，不保证“记得全”。

### 8.7 清空全部数据（危险区，不可撤销）

位置：**设置 → 长期记忆 → 危险区 → 「清空全部数据（不可撤销）」**。
这一项清的是**所有人**的数据，所以它**不在**任何人的详情页里 —— 列表态就能直接看到。

**流程**

1. 点按钮 → 弹框**只拉清单**（还不生成验证码）；
2. 清单分两栏逐项列出「会删除」与「会保留」；
3. 点「我明白，生成验证码」→ 出现 **8 位十六进制码**（每次开弹框重新生成，5 分钟有效、不可鼠标选中）；
4. 输入该码 → 「确认清空（不可撤销）」；
5. 程序把要删的文件**先备份**，逐项校验通过后才真删；删完**立即自动重启**。

**验证码四态**（可预期，不是随机行为）

| 情形 | 表现 |
| --- | --- |
| 没生成过码就点确认 | 提示「还没有验证码」 |
| 输错第 1、2 次 | 留在弹框、清空输入、**码不变** |
| 输错第 3 次 | 弹框关闭 + 危险区内提示「删除失败」（数据未被删除） |
| 超过 5 分钟 | 提示「验证码已过期，请重新生成」 |

验证码的真值**只在主进程**，前端只负责显示 —— 打开 DevTools 也改不动判定。

**删除面（5 项）**

- `sessions.json`（写回 `[]`）；
- `memory.db` 的三张表（记忆 / 人设历史 / 用户人设）；
- `stories/`（整目录，含每个故事自己的记忆库）；
- `summaries.json`（对话摘要 —— 摘要会被无条件注入，所以它也算“记得的东西”）；
- `zones.json.retired-bak`（P6 删区块时留下的历史副本）。

**保留面（11 项）**

`settings.json`、`channels/`（**授权 —— 删数据不删人，清完你仍然能对话**）、`observe/`、
`snowluma/`、`presets/`、`workspace/`、`qq/settings.json`、`memory.db.p5-backup`、
`models/`、`Local Storage /` 与 `Cookies`（内容未验证，宁少不清）。

**备份与中止**

- 备份目录是 `%APPDATA%\Nahida Chat.p7-backup-<时间>`，与数据目录**同级**（同一块盘）；
- SQLite 库走 `VACUUM INTO` 一致性快照，并跳过 `-wal` / `-shm` 侧车（空 WAL 是正常状态，不是坏文件）；
- **备份不成立就中止，一个字节都不删**。这是这个功能唯一的安全网。
- 想防整盘故障，请自己再往**另一块盘**备一份 —— 程序自建的这份救不了盘坏。

**重启**：清空后应用会自己重启。开发模式（`pnpm dev`）下是**重拉整条 dev 链路**，
所以会看到终端退回命令行、几秒后新窗口自己出现（细节见 12 与 11.4）。

## 9. 记忆域与渠道（QQ）

### 9.1 记忆域：区块已移除（P6）

早期版本有一套「区块（Zone）」，用来给不同渠道会话划分共享记忆域。**它已被整体移除**：

- 设置页不再有区块入口，`userData/zones.json` 不再被读写（如果你还留着旧文件，它不会再影响任何行为，可自行删除或留档）；
- 相关代码（`features/zones`、`ipc/zones`、`shared/zones`、`ZonesSection`）与测试一并删除；
- **不需要数据迁移**：记忆的真实分区键一直是 `(user_id, persona_id)`，
  区块字段只在会话路由上充当一个“非空闸门”，从未参与行级过滤 —— 删掉它不影响任何已有记忆。

现在记忆怎么分：

| 维度 | 规则 |
| --- | --- |
| 人的隔离 | 按 `user_id` 分；QQ 是发送者 QQ 号，桌面是 `root` |
| 人设的隔离 | 按 `persona_id` 分；同一个人换人设 = 换一套记忆 |
| 场景 | **不参与分区**。桌面 / 私聊 / 群聊共享同一份 `(user_id, persona_id)` 记忆（“换场景不换人设”） |
| 故事 | 物理隔离：每个故事自己的 `stories/<storyId>/memory.db` |
| 群语料 | `observe/` 是**只增不清**的原始语料，不进记忆、不参与注入 |

> 想让某个场景的记忆彻底分开，正确做法是用**故事区**（各自独立的库），而不是期待模块再切一层。

### 9.2 渠道控制台

**设置 → 渠道控制台**按“人”授权，核心数据是真源 `userData/channels/access.json`：

- **QQ 号白名单**：一行一个号，分别控制私聊、群聊、工具三个权限位；
- **群白名单**：决定某个群是否允许她说话；
- **鉴权开关**：
  - 群成员鉴权（默认关）：开启后，账号表中的“群聊”位才生效；
  - 工具调用拦截（默认开）：不允许的人不能执行工具；
  - 群聊工具增强（默认开）：群聊里的工具供给；
- **渠道工作区**：QQ 会话唯一允许落地的文件根，默认 `userData/workspace`；
- **渠道模型**：跟随默认档案的默认模型；
- **旁听库**：只增不清的群语料，只读，不参与记忆注入；采集资格由 QQ 桥规则决定（群不需要加白名单也会被旁听）。
  面板上只留一行概要（几个群 / 几个私聊 / 多少行语料），群号明细收进 **「群号一览（可搜索）」** 弹层：
  按群号、群名、账号搜，空格分隔多个词时要求同时命中（例如「群聊 1234」），命中行里可以直接「看最近」。

只有两层都满足，群里才有工具可用：**群聊工具增强开关打开 + 账号的“工具”位勾选**；最终还要看全局工具权限模式。

### 9.3 QQ 接入步骤

1. 先启动并登录 QQ；
2. 打开 **设置 → QQ 接入**，点“刷新”查看本机 QQ 主进程；
3. 在目标 PID 行点 **注入**。程序不会自动挑进程；
4. 状态变为“在线/已注入”后，去 **设置 → 渠道控制台** 配置账号/群白名单；
5. 在群里通常需要 @ 她（可在 QQ 接入 → 行为开关里调整）；
6. 观察 **最近事件** 确认回复/丢弃原因。

如果宿主降级，QQ 接入页会提示；先确认 `out/snowluma-host` 下的 `node.exe` 与 `index.mjs` 存在，再点“重启宿主”。

### 9.4 QQ 行为开关

在 **设置 → QQ 接入 → 行为开关** 可以调整：

- typing 提示方式与文本（仅私聊）；
- 群里是否必须 @；
- 群聊首段是否 @ 提问者；
- 分段延迟、最大段数、单段码点上限；
- 每用户/每渠道 60 秒限速；
- 出错时是否回复一句提示。

这些设置控制出站观感与限流，不代替渠道授权。

## 10. 数据、备份与隐私

### 10.1 主要数据位置

路径中的 `userData` 可在 **设置 → 关于 → 数据目录** 查看。典型文件/目录：

| 路径 | 内容 |
| --- | --- |
| `settings.json` | 模型档案、工具权限、记忆参数、对话摘要参数、工作区、外观 |
| `sessions.json` | 普通会话、故事分支会话、旁白、思考过程与消息历史 |
| `memory.db` | 主长期记忆库（RAG 事实记忆） |
| `summaries.json` | 对话摘要（每会话一份：游标 + 四段文本） |
| `stories/<storyId>/` | 故事元信息、分支、画像、独立记忆库 |
| `memory.db.p5-backup` | 改造记忆分库之前的旧库副本（只读留档，程序不依赖它运行） |
| `zones.json` | **已不再读写**（区块在 P6 移除）；旧文件留着无害，可自行删除 |
| `stories/.trash/` | 删除故事区前的自动备份 |
| `channels/access.json` | 渠道按人授权与群白名单 |
| `workspace/` | 默认工作区 / 渠道工作区 |
| `snowluma/` | QQ 宿主运行时数据 |
| `models/` | 本地 embedding 模型（不随仓库分发） |

提示词不在 userData 内，而在应用根的 `Prompt/`（开发模式是仓库目录，打包后可能是 `resources/prompt`）。

### 10.2 建议备份

最小备份集合：

- `settings.json`
- `sessions.json`
- `memory.db`
- `summaries.json`（对话摘要；丢了不会丢聊天记录，但已压缩的窗口外内容会退回全量重压）
- `stories/`
- `channels/access.json`
- `Prompt/`

备份前先退出应用，避免 SQLite 的 `-wal` / `-shm` 文件没有被正确回收。

**「清空全部数据」自带备份**：执行前会把删除面里的每一项复制到
`%APPDATA%\Nahida Chat.p7-backup-<时间>`（与数据目录同级），备份校验不通过就**不删**。
注意这份备份和原数据在**同一块盘**，防不了盘坏；需要的话请自己再往另一块盘备一份。
另外每清一次就多一个这样的目录，程序不会自动清理，久了会占地方。

### 10.3 隐私与安全边界

- 桌面会话历史、故事、记忆库、世界书与提示词均在本机；
- `apiKey` 当前明文存在 `settings.json`，**尚未加密**；
- 使用远程模型时，提示词、上下文、工具结果与记忆命中会随请求发送给模型服务商；
- QQ 接入会把相关消息交给 QQ 客户端/宿主，并按配置回复；
- 工具的“完全访问”模式不受工作区限制，请只在信任模型与当前任务时使用；
- 审批模式下有副作用工具会等待确认，超时按拒绝处理；QQ 没有审批卡，因此审批模式下的副作用工具在 QQ 中等于拒绝；
- 不要把 `settings.json`、`sessions.json`、`memory.db` 或含密钥的日志提交到公开仓库。

**截图只截改动部分。** 网格图是「这次改动」的证据，不是产品目录，所以出图要指名道姓：

### 11.4 「清空全部数据」之后的重启怎么走

这一段写给**自己跑开发环境**的人：清空后的重启，开发模式和打包版不一样。

| 环境 | 重启方式 | 你要做的 |
| --- | --- | --- |
| `pnpm dev`（开发模式） | **重拉整条 dev 链路**（vite dev server + electron） | 什么都不用做，**等 3–8 秒**，新窗口自己出现 |
| 打包版 / 没有 dev server | Electron 原生 `app.relaunch()` | 同上，等窗口 |

开发模式为什么要这么绕：窗口加载的是 `ELECTRON_RENDERER_URL`，而那个 vite dev server 住在
`electron-vite` 进程里 —— 旧 electron 一退，dev server 跟着退。此时若只重启 electron，
新窗口会去连一个已经关掉的端口（`ERR_CONNECTION_REFUSED`），看到的就是白屏。
所以开发模式下必须把 dev server 一起拉起来。

> 两条容易误会的事：
> 1. 终端里的 `pnpm dev` **会退回命令行**，这是正常的 —— 新的 dev 链路在后台跑，stdio 被丢弃所以没有输出；
> 2. **不要**这时候手敲 `pnpm dev`：单实例锁会把后起的那个顶掉，看起来又像失败了。

## 12. 安装与发布

### 12.1 安装包

`pnpm package:win` 产出 NSIS 安装包：`release/Nahida-Chat-Setup-<版本>-x64.exe`。

- 可选安装目录（非 one-click）；
- 自带 Electron 运行时与 **Snowluma 宿主**（含 `node.exe` 与原生模块），
  **用户机器不需要装 Node / pnpm**，也不需要跑任何构建命令；
- 宿主与提示词库作为**独立资源**随包分发（`resources/snowluma-host`、`resources/prompt`），
  不塞进 `app.asar` —— 原生的 `.node` 与 `node.exe` 必须能在磁盘上被加载与执行。

### 12.2 发布门禁

打包前后各校验一次宿主资源（13 个必需文件 + 全量 SHA-256 清单）：

| 时机 | 校验点 | 不通过 |
| --- | --- | --- |
| `beforePack` | 源目录 `out/snowluma-host` | **中止打包** |
| `afterPack` | 产物 `resources/snowluma-host` + 提示词库 | **中止打包** |

这样能挡住「开发机上能跑、发出去缺文件」这一类问题。

### 12.3 升级与数据

- 安装包只覆盖程序目录，**不碰** `%APPDATA%\Nahida Chat`（会话、记忆、故事、设置都在那里）；
- 下载的 embedding 模型也在 userData 下，升级后仍可用；
- 升级前仍建议备份 `userData` 与 `Prompt/`（见 10.2）。

## 13. 已知边界与未完成项

以下内容在当前版本中**不存在**或仍有明确限制：

- **没有自动更新**：安装包已能产出，但程序不会自检新版本，升级要重新安装；
- `apiKey` 没有使用 Electron safeStorage 加密；
- **ST 桥接需要你自己启动 ST**：NC 不托管 ST 进程，ST 没起时该开关不生效（会按原路径生成）；
- **ST 桥接只作用于故事模式**，且渠道会话即使写着 story 也不走桥接；
- **ST 里的预设脚本产物如果是 HTML 宿主**（`<iframe>`/`<style>` 那一类），NC 只抽取文本做折叠卡，
  不渲染原 HTML —— 所以和 ST 里的观感不会完全一致，这是刻意的边界（iframe 宿主永久不做）；
- 没有多窗口与多主题皮肤；主题仅浅色/深色/跟随系统；`Ctrl/Cmd + Shift + G` 只用于开发态 UI 网格，不是业务快捷键；
- 工具集当前只有只读的目录列表、读文件与时钟；没有通用写文件/命令执行工具；
- QQ 注入依赖本机 QQ 与 Windows 宿主环境，不保证所有 QQ 版本可用；
- 故事区与普通会话的侧栏是分开的，故事不会出现在“最近”；
- **区块已移除（P6）**：设置里没有区块入口，`zones.json` 不再读写；
  它的删除**不需要数据迁移**（记忆分区键一直是 `(user_id, persona_id)`）；
- **思考过程会落进 `sessions.json`**：可以做展示回看，但推理模型单轮几万字，长对话下这个文件会明显变大；
  目前没有「不保存思考」的开关（要加只涉及渲染层偏好，不动契约）；
- **切角色不换记忆库**：长期记忆按用户人设分域，不按 AI 角色分域，所以换角色后仍会召回同一批事实记忆；
  要隔离记忆请用故事区（8.4）；
- **故事会话的角色只能在设置里改**：对话页那个选择器在故事里是置灰的（角色属于故事区本身）；
- **删单条分支没有备份**：只有删除整个故事区才会先备份到 `stories/.trash/`；单条分支删掉就是连同它的会话消息一起没了（最后一条分支删不掉）；
- **「清空全部数据」不覆盖 `Local Storage` / `Cookies`**：那里可能是界面折叠态，也可能是登录态，
  内容未经核实，按“宁少不清”处理；
- **清空后的备份目录会累积**：每清一次多一个 `Nahida Chat.p7-backup-<时间>`，程序不自动清理；
  且它与数据在同一块盘，防不了盘坏；
- **清空是全局的**：没有“只清某个时间段”或“撤销” —— 想留就先自己备份；
- 旧数据迁移路径存在，但升级前仍建议备份 `userData` 与 `Prompt/`。
