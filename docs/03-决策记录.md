# 03 · 决策记录（ADR）

> 状态：已定稿。这三条是产品基调，改动需要同步改本文档与路线图。

## ADR-0001 · 数据纯本地

**决策**：不做云同步、不做账号体系、不设计多端一致性协议。所有数据只存在本机。

**落地方式**：M1 把 `sessions.json` 迁到 SQLite，用 Electron 内置的 `node:sqlite`。

**为什么用内置而不是 better-sqlite3**：已在 Electron 45（Node 24.22）里实测：

```
node:sqlite=OK exports=DatabaseSync/StatementSync/Session/constants/backup
query=[{"a":42}]
```

`DatabaseSync` 是同步 API，主进程里直接调即可；且**没有原生模块**，不需要 `electron-rebuild`，
也就不会出现"换个 Electron 版本就得重编译、换台机器就跑不起来"的经典事故。

**代价**：单机丢了就是丢了。M4 再补"导出/导入整库"作为兜底，不上同步。

**放弃的方案**：JSON 整文件重写（消息一多 O(n) 写放大，实测 1000 轮后每次落盘都要重写全量）；
sql.js（wasm，够用但多一层内存文件系统，没必要）。

## ADR-0002 · 模型兼容全做

**决策**：OpenAI 兼容 / Anthropic / Gemini / Ollama 四类适配器全部实现，外加离线 mock。

**落地方式**：provider 契约统一成"事件流"，适配器只做格式翻译，不做业务：

```ts
type ProviderEvent =
  | { type: 'text'; text: string }
  | { type: 'tool_call'; call: ToolCallRequest }
  | { type: 'finish'; reason: string }
```

工具调用的**循环逻辑写在 chatService，不在适配器里**。四个适配器各自负责把自己那边的
tool_call 增量格式（OpenAI 的 `delta.tool_calls[i].function.arguments` 分片、
Anthropic 的 `input_json_delta.partial_json`、Gemini 的 `functionCall.args`、Ollama 的
`message.tool_calls`）翻译成同一个 `ToolCallRequest`。

**代价**：四份 SSE/NDJSON 解析代码要各自维护；协议升级就得跟着改。
**缓解**：每个适配器都只依赖 `fetch` + 手写解析，不引入 SDK，避免被 SDK 的小版本绑架。

## ADR-0003 · 要工具能力（最先立规矩的一条）

**决策**：做工具调用，但**默认不安全**——默认权限模式是「审批」。

> **2026-10 修订**：初版用的是「按风险分级（read/write/network/exec）+ 目录白名单」。
> 用了一轮之后发现，风险分级是个分类学问题而不是行为问题：用户既读不懂「联网类操作该允许还是询问」，
> 也没法判断自己配得对不对，配错了还给人虚假的安全感。已改成下面的三模式方案。

**三道闸，缺一不可**：

| 闸 | 位置 | 作用 |
| --- | --- | --- |
| 1. 权限模式 | `settings.permission.mode` | 完全 / 只读 / 审批，见下表 |
| 2. 人在环审批 | IPC `chat:approval` ↔ 渲染层审批卡 | 「审批」模式下弹卡，超时 120s 自动拒绝 |
| 3. 工作区路径闸 | `settings.permission.workspaceDir` | 非完全访问模式下，文件工具只能碰工作区内的路径 |

**三种权限模式**：

| 模式 | 只读工具 | 有副作用的工具 | 路径限制 |
| --- | --- | --- | --- |
| 只读 `readonly` | 直接执行 | 一律拒绝 | 限工作区内 |
| 审批 `approve`（默认） | 直接执行 | 弹卡确认 | 限工作区内 |
| 完全访问 `full` | 直接执行 | 直接执行 | 不限 |

工具不再声明风险等级，只声明 `readOnly: boolean`——一个用户能自己回答的问题：
「这个工具会不会改东西？」策略据此判定，见 `src/main/features/tools/permission.ts`。

**为什么必须现在做**：工具一接上，提示词注入就从理论问题变成真实问题——
一封邮件、一段网页、一个用户粘贴的报错，都可能让模型去调 `fs.read_file` 读 `~/.ssh/id_rsa`。
第 3 道闸就是为这种情况准备的：**模型被策反了，也读不到工作区外的路径**
（除非用户自己切到了「完全访问」——那是显式的知情选择，不是意外的默认）。

**明确不做**：不做"一次授权永久生效"的全局开关；`remember` 只在当前进程内生效（工具名级别），
重启即失效，切换权限模式时也会清空。宁可烦一点，不要静默执行。

**已知局限**：
- 审批卡只显示参数原文，不做语义风险解释（M3 后期补"这次调用会读到什么"的预览）。
- 写入/执行类工具目前没有实现，但 `readOnly: false` 的判定路径已经就位，
  将来接入时不需要回来改权限代码。
- 「完全访问」下路径闸会整体失效，这是设计取舍：模式本身已经表达了知情同意，
  再偷偷留一道目录限制只会让模式名撒谎。
